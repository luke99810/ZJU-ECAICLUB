# AI Club 社团官网

浙江大学工程师学院人工智能俱乐部官网。按 `AI Club 社团官网｜完整架构设计方案.md`
实现：**单站点、双模块**（对外展示 + `/admin` 成员后台），外加社团特色的 AI 工具。

> **要上线看这个** → [`上线指南.md`](上线指南.md)
> 从"本地能跑"到"社团在用"的完整步骤：建库、接登录、填密钥、部署，以及上线前检查清单。
> 本文件只讲现在有什么、怎么用。

## 跑起来

```bash
npm install
npx next dev -p 3007      # http://localhost:3007
```

AI 客服小艾需要一个免费大模型 key（不填也能跑，退化成站内检索）：

```bash
cp .env.example .env.local   # 填 AI_API_KEY，然后重启 dev server
```

站点自己的 AI 能力集中在右下角的 **AI 客服「小艾」**（全站悬浮）：先在站内检索
项目 / 学习资料 / 论坛帖 / 新闻 / 成员，再依据检索结果与资料文档作答，并把命中的条目
做成可点结果卡。**没有 AI key 时也能用** —— 退化成纯站内检索，照样能把项目找出来。

`/tools` 是**外部工具索引**（点卡片跳工具官网，本站不代理任何服务），
和上面的「小艾」是两回事 —— 前者是别人的能力，后者是本站的能力。

## 当前状态：前端完整，后端未接

方案要求的 Supabase 与 Cloudflare 尚未开通，所以：

- **数据**存在浏览器 localStorage 里，首次访问自动灌入 `src/data/seed.ts` 的演示数据。
  换浏览器或清缓存会回到初始状态。
- **登录**有真实口令校验（SHA-256 + 每账号随机盐，不存明文），但**整套校验跑在浏览器里** ——
  改 localStorage 就能绕过。**上线前必须换成 Supabase Auth**。

  账号规则：
  - 初始管理员：**本地演示模式**下内置一个引导账号，账号与出厂口令见
    `src/data/seed.ts` 与 `src/lib/password.ts`（仅供本地把后台点通用）。
    接了 Supabase Auth 之后这套完全不生效 —— 真账号在 Supabase 控制台建，
    口令由本人保管，仓库里不留任何口令。
  - 管理员在「成员管理」录入学号 + 邮箱开通账号，**初始口令即本人学号**，成员登录后自行修改。
  - 管理员最多 **3 个**（含初始那一个），名额满时表单里的「管理员」选项会被禁用。
  - 忘记口令：管理员在「成员管理」点「重置口令」回退到学号。
  - 登录账号可填**学号或邮箱**。

  部门与权限：
  - 部门共四个：**管理层 / 技术部 / 组织部 / 宣传部**，与社团实际架构一致。
  - **「管理层」等价于管理员** —— 录入时选管理层即获得管理员权限，不再单独设「权限」
    字段（两个字段并存必然出现「部门管理层但权限成员」这种自相矛盾的记录）。
    调部门会同步调权限。管理层名额上限 3 人，满了下拉里该选项自动禁用。
  - 管理员都可以添加成员。

  内容编辑权限：
  - **活动 / 成果 / 公告**：任何登录成员都能新增和编辑（社团内容以协作为主，
    每条记 `edited_by` 留痕）；**删除限管理员**。
  - **项目审核**：所有登录成员都能审，通过后才对外展示。
    - **管理员（管理层）**：审全部 —— 成员提交的 + 校友 / 校外投稿。
    - **普通成员**：只审公开投稿（校友 / 校外）。成员自己的项目一律由管理层把关，
      「自己提交自己通过」的口子从根上就不存在。普通成员的审核列表里
      直接看不到成员提交的项目（数据层过滤，不是界面禁用）。
  - **成员资料**：本人改自己的（`/admin/account`）；管理员可改任何人的
    （`/admin/members` 的「改资料」）。学号/邮箱只能由管理员在成员管理里动。
  - **AI 项目**：作者管自己的内容。改动已通过的项目会打回重审。
- **AI 工具**已经是真的：填了 key 就能用，请求经服务端中转，密钥不下发浏览器。

这三层都做了接口隔离，接真服务时页面代码不用改：

| 换什么 | 改哪个文件 |
| --- | --- |
| 数据库 | `src/lib/store/`（**已就绪**：local / supabase 两套实现按环境变量自动切换） |
| 登录 | `src/lib/auth.ts` + `src/lib/password.ts`（`signIn` / `signOut` / `getSession` / `onAuthStateChange`） |
| 小艾的人设与资料 | `src/lib/settings.ts`（现在只存管理员本机，换成 `site_settings` 表后才全站生效） |
| AI | 已就绪，只需填 `AI_API_KEY` |

## 投稿与来源判定

**三类内容都能投**：学习资料 / 项目共享 / AI 论坛。入口在 `/community` 的「我要投稿」
区块（各板块页里也各有一个，方便看着列表顺手就投）。

- **公开投稿**（任何人，不用登录）—— `SubmitProjectModal`（项目，字段多）
  与 `SubmitContentModal`（资料 / 发帖，字段少）。都要填姓名 +
  **联系邮箱（必填）**。邮箱不只是联系方式，它决定这条投稿的来源档位：

  | 邮箱 | 来源 | 谁能审 |
  | --- | --- | --- |
  | 在册成员的邮箱 | — | **拦下来**，提示去登录提交（项目才会挂到他名下） |
  | `zju.edu.cn`（含子域，如 `stu.zju.edu.cn`） | `alumni` 校友投稿 | 任何成员 |
  | 其他后缀 | `external` 校外投稿 | 任何成员 |
  | 成员后台提交 | `member` | **仅管理层** |

  这三档对三类内容一视同仁：普通成员只审 `alumni` + `external`，成员自己提交的
  必须管理层审 —— 「自己提交自己通过」的口子从数据查询那一层就不存在，
  而不是靠界面禁用按钮。

  判定在 `src/lib/submission.ts`。后缀匹配用的是 `host === domain || host.endsWith('.'+domain)`，
  所以 `a@zju.edu.cn.evil.com` 这种伪造会被正确判为校外。

- **成员登录提交** —— 项目走 `/admin/projects`，挂在本人名下、出现在「我的项目」；
  资料与发帖走同一个弹窗，登录后自动带身份，不必再填联系方式。

投稿人的联系邮箱**只在审核界面显示**，对外页面的 HTML 里都搜不到。

**唯一不审核的是论坛评论** —— 未登录访客也能直接评（称呼留空记作「访客」），
这是「外部访问只能评论」的落点。所以 `ForumComment` 这张表刻意没有 `status` 字段。

## 留言与统计

**留言**：`/contact` 的表单会真的写进 `messages` 表，后台 `/admin/messages` 能看到。
状态是 **待处理 / 已处理 / 已忽略**，不是投稿那套 pending / approved ——
留言不对外展示，它是个待办队列，不是发布流程。所有登录成员都能处理（留言积压比
误处理更糟），处理人会记在留言下面；删除限管理员。站点本身不发信，回复走 `mailto:`。

**统计视图**在 `/admin` 概览下半部分，五块：内容累计增长（折线）、每月新增（柱状）、
成员部门分布、内容来源构成（环形），以及**内容贡献榜**（谁发得最多，可按三类内容切换，
默认前 5、可展开到前 10）。可按近 6 / 12 / 24 个月 / 全部筛选。

图表是**自己用 SVG 画的**（`src/components/charts/`），没装图表库：三种图加起来
两百来行，而 recharts 之类要拖进 100KB+，且这个项目已经被 `lucide-react`
大版本删接口坑过一次。带四张图的概览页打包后只有 5.34 kB。

几个口径，看图前先知道：

- **只统计已通过的内容** —— 待审和被驳回的不算，否则图会比实际公开的多一截；
- **按月聚合** —— 社团一个月几条内容，按天画是一条贴着 0 的线；
- **累计线的起点带上时间窗之前的存量** —— 否则「近 6 个月」会从 0 开始，像刚成立；
- **时间范围作用于所有内容类统计**（累计、新增、来源构成、贡献榜），
  只有「成员部门分布」始终看全量 —— 那是人员现状，跟选了几个月没关系；
- 贡献榜按 `author_id` 归并；公开投稿没有账号，只能按姓名归并，
  **同名的校外投稿人会被并到一起**，这是没有账号体系时的必然妥协。

## 成员资料与往届判定

社团成员页展示的每一项（姓名 / 部门 / 加入年份 / **兴趣方向** / 简介 / 技术标签）
后台都能改，不存在「前台显示了但没地方填」的字段。管理员在 `/admin/members` 改任何人的，
成员本人在 `/admin/account` 改自己的。

方向信息分两个字段，别合并：

- **技术标签** 取自固定词表（LLM / Agent / RAG …），用来**按技术筛人** —— 固定才筛得动；
- **兴趣方向** 自由文本（如「智慧交通」「柔性直流输电」），用来**说清楚这人在做什么** ——
  成员的研究方向经常落在那十个标签之外，只有固定词表会逼着人乱选一个凑数。

**往届不是手工勾的字段**，由加入年份推导（`isAlumniMember`）：加入年份距今满
`ACTIVE_YEARS` 年即归入往届，每年自动滚动。当前 `ACTIVE_YEARS = 1`，
也就是「今年加入的是现任，往年加入的都是往届」；社团若按两年一届算，
改 `src/types/index.ts` 里这一个常量即可。

手工标记这种字段一定会忘记维护 —— 换届时没人会记得挨个去勾。

## 成员批量导入

`/admin/members` 支持 **CSV / XLSX** 批量开通账号（`src/lib/memberImport.ts`）。
取向是「宽松地读、严格地报」：

- 表头认中英文多种写法（`姓名/name`、`学号/studentid`、`兴趣方向/研究方向`、`加入年份/year`…），
  没认出来的列会在预览里列出来告诉你被忽略了；
- **先出预览再写库**，不做「选了文件就直接导」；
- 每一行的问题单独成句（第几行、什么毛病、跳过还是按默认处理），
  而不是整批失败或静默跳过 —— 名单是要对人负责的数据；
- 批量导入**不允许**设成「管理层」，管理员必须一个个加；
- 文件内重复与库内已存在分两处拦，报错位置才直观；
- 单次上限 300 行，页面上有「下载模板」。

导入的成员初始口令同样是**本人学号**。

## 标签体系

项目有两套正交标签，项目共享页两行筛选可叠加：

- **功能标签**（回答「能帮我干什么」，卡片上是绿色，排在前面）：
  内容创作、图像视频生成、数据挖掘、智能对话、代码开发、科研辅助、音频生成、日常规划、工程应用
- **技术标签**（回答「用了什么」，蓝色）：
  LLM、Agent、RAG、MCP、Multimodal、NLP、CV、RL、Robot、Deployment

改词表要同时改 `src/types/index.ts` 与 `src/lib/aiPrompts.ts`（两份必须一致，
后者给 AI 打标签当白名单用），并把 `src/lib/store.ts` 的存储 key 升一版 ——
否则本地旧数据会留下一堆筛不出来的僵尸标签。

后台表单里两类标签**各有一个 AI 自动按钮**，用的是两个独立提示词：技术标签看
「用了什么技术」，功能标签看「用户拿它能完成什么任务」。

## 封面图

项目与活动的封面**上传本地图片**，不填 URL —— 学生手上通常没有图床。
浏览器里用 canvas 压到最长边 600px、JPEG，逐级降质量直到 400KB 以内
（实测 2.8MB 的 2400×1600 压到 6KB），存成 data URL 直接入库。

接了 Supabase 之后应换成 Storage 上传、库里只存 URL —— data URL 会随每次查询
一起传输，图多了拖慢列表。改 `src/lib/compressImage.ts` 与 `CoverUpload` 即可。

## 文档解析

AI 写作助手能吃 PDF、Word（.docx）、Markdown、txt/csv/json。**解析全在浏览器里做，
原文件不上传服务端**，只有提取出的文字随 AI 请求发出去 —— 这样没有上传体积限制，
也绕开了 Cloudflare 边缘运行时跑不了 Node 解析库的问题。

- PDF：`pdfjs-dist`，worker 从 `public/pdf.worker.min.mjs` 加载。
  这个文件由 `npm run copy-pdf-worker` 从 node_modules 拷过来，已挂在 `postinstall`，
  重装依赖会自动更新。**扫描版 PDF（纯图片）提不出文字**，会提示先做 OCR。
- Word：`mammoth`（只支持 .docx；旧版 .doc 是二进制格式，会提示另存为 .docx）。
- 单个文件 ≤ 10MB，提取后截到 6000 字（与 `/api/ai` 的输入上限对齐），
  截断时界面上会写明原文多少字。

两个解析库都是**按需动态 import**，只粘贴文字的人不会下载它们。

## 接 Supabase

完整步骤（含接 Auth、部署、检查清单）见 [`上线指南.md`](上线指南.md)，这里只列要点：

1. 建项目，在 SQL Editor 里执行 [`supabase/schema.sql`](supabase/schema.sql) —— 八张表
   （members / ai_projects / posts / resources / forum_posts / forum_comments /
   tool_links / messages）+ RLS 策略 + 审核状态写保护 trigger。
2. `.env.local` 填 `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY`。
3. **数据层不用改代码** —— `src/lib/store/` 下已经有两套实现（`local.ts` / `supabase.ts`），
   `index.ts` 按环境变量二选一，填了变量就走真库。`auth.ts` 仍需手动换成 Supabase Auth。
4. 可选：执行 [`supabase/seed.sql`](supabase/seed.sql) 带上那 25 条 AI 工具导航。

⚠️ **接完数据库紧接着就要接 Auth，中间不要对外发布。** 现在的口令校验整套跑在浏览器里，
改 localStorage 就能提权 —— 数据还在本地时这只是假数据，接了真库之后改的就是真库。

schema.sql 里有两处值得先看一眼再执行：

- 三类投稿的 **insert 策略强制 `status = 'pending'`**。少了这一条，外部投稿可以
  带着 `status='approved'` 直接插进来，审核就形同虚设。
- **`guard_review_status()` trigger** 卡住非管理员改 `status` / `review_note`，
  只对「成员审 alumni / external」这一种情形放行。光靠 update 策略挡不住 ——
  作者能改自己的行，也就能把自己的投稿改成已通过。

## 部署到 Cloudflare Pages

站点里有一个服务端接口（`/api/ai`，用于隐藏 AI 密钥），所以纯静态导出不能直接用。
两条路，二选一：

**A. `@cloudflare/next-on-pages`（推荐，改动最小）**

```bash
npm i -D @cloudflare/next-on-pages
npx @cloudflare/next-on-pages
```

Pages 构建命令设为 `npx @cloudflare/next-on-pages`，输出目录 `.vercel/output/static`。
API route 会被编译成 Pages Function，本地 `next dev` 的行为与线上一致。

**B. 静态导出 + Pages Function**

`functions/api/ai.ts` 已经写好了 Cloudflare 版的等价实现（与 Next 那个共用
`src/lib/aiPrompts.ts`，保证行为一致）。走这条路需要：
在 `next.config.js` 加 `output: 'export'`，并**删掉 `src/pages/api/ai.ts`**
（`output: 'export'` 不允许 API route 共存）。代价是本地开发要用
`npx wrangler pages dev` 才能调 AI 接口。

两条路都需要在 Cloudflare 控制台配环境变量 `AI_API_KEY`（以及可选的
`AI_API_BASE` / `AI_MODEL`）。
